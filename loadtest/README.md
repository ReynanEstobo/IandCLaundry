# I&C Laundry load test

Measures how many people can use the system at the same time before it slows
down. It simulates three kinds of users, using the same requests as the real
screens:

| Simulated user | What they do |
|---|---|
| Branch staff | Keep the staff dashboard and Orders list open (refreshed every 30 seconds, as the app does), and take orders from creation through processing, ready, and collect-and-release |
| Administrator | Keeps the admin dashboard open and loads 30 days of Analytics every few refreshes |
| Customer | Looks up an order on the public tracking page |

The test raises the number of simultaneous users stage by stage (5, 10, 20, 40,
80 by default, two minutes each) and stops when the slowest 5% of actions take
longer than 5 seconds or more than 2% of requests fail.

## Safety

- It runs against a **separate test Supabase project** and a **test copy of the
  backend on your computer**. The scripts refuse to run if the settings point at
  the live Supabase project or the live website.
- Email, SMS, AI and Turnstile keys are blank in the test settings, so nothing is
  sent and no paid quota is used.
- Test passwords are generated by the scripts and saved only in
  `loadtest/.accounts.json`, which git ignores, like `loadtest/.env.loadtest`.
- `scripts/reset-and-seed-test-data.sql` **deletes data**. It and
  `scripts/seed-forecast-history.sql` run only in a database that
  `setup-1.sql` has marked as a test copy, so they stop without changing
  anything if they are run in the live project. The setup itself stops if it is
  pasted into a database that already has I&C Laundry data.

## One-time setup

1. **Create a test project.** In Supabase, click **New project**, name it
   `ic-laundry-loadtest`, and pick the same region as the live project. (The
   free plan allows two active projects.)
2. **Add its keys.** Copy `loadtest/env.loadtest.example` to
   `loadtest/.env.loadtest`. From the *test* project's **Project Settings → API**,
   fill in `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY`.
3. **Create the database.** Run:

   ```bash
   node loadtest/build-setup-sql.mjs
   ```

   It writes `loadtest/out/setup-1.sql`, `setup-2.sql` and `setup-3.sql`. In the
   test project's **SQL Editor**, paste and run each file in order, one at a time.
   Each should end with "Success".
4. **Create the test accounts** (1 administrator and 3 staff per branch):

   ```bash
   node loadtest/seed-accounts.mjs
   ```

5. **Add realistic data.** In the test project's SQL Editor, paste
   `scripts/reset-and-seed-test-data.sql`, replace its empty confirmation text
   with `RESET_TEST_DATA_ONLY`, and run it. Then run
   `scripts/seed-forecast-history.sql`.
   Together they add demo services, inventory, about 960 customers and about 970
   orders over 90 days, similar to the live database today.

## Running the test

Use two terminals.

1. Start the test backend and leave it running:

   ```bash
   node loadtest/start-test-server.mjs
   ```

2. Start the load test (about 10 minutes with the defaults):

   ```bash
   node loadtest/run.mjs
   ```

Options, all optional:

| Option | Default | Meaning |
|---|---|---|
| `--stages 5,10,20,40,80` | 5,10,20,40,80 | Simultaneous users in each stage |
| `--stage-seconds 120` | 120 | How long each stage runs |
| `--poll 30` | 30 | Seconds between screen refreshes (the app uses 30) |
| `--mix staff:70,admin:15,customer:15` | 70/15/15 | Share of each kind of user |
| `--max-p95 5000` | 5000 | Stop when the slowest 5% of actions exceed this many milliseconds |
| `--max-errors 2` | 2 | Stop when more than this percentage of requests fail |

## Reading the results

For each stage the test prints the number of requests, the error rate, and for
each action its typical time and the time the slowest 5% exceeded. The last line
says how many simultaneous users the system handled within the limits. Full
details are saved in `loadtest/out/report-<date>.json`.

What the result does and does not show:

- It measures your **database plan and backend logic** under shared load, which
  is where the live system would slow down first.
- The test backend runs as **one process on your computer**. The live site runs on
  Cloudflare Workers, which add capacity automatically, so if your computer's CPU
  is busy at 100% the limit you see is your computer, not the system. Watch Task
  Manager during the test.
- Your internet connection to Supabase is part of every request, as it is for
  the live Worker.
- Gemini, email and SMS are not part of the test.

## Checking the tool without Supabase

These run entirely on your computer and never connect to any database:

```bash
node loadtest/build-setup-sql.mjs --verify
```

```bash
node loadtest/dry-run-seed.mjs
```

```bash
node loadtest/run.mjs --mock
```

## Cleaning up

When finished, delete the test project in Supabase (**Project Settings →
General → Delete project**).
